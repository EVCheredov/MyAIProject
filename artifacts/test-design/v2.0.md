# ТЕСТ-СЬЮТ 01: Позитивные сценарии (Happy Path)

---

#### ТЕСТ-КЕЙС: TC-SCN-001-01 — Успешная авторизация с валидным сертификатом КЭП
* **Тест-сьют:** 01 — Позитивные сценарии (Happy Path)
* **Тип проверки:** Позитивная
* **Приоритет:** Critical
* **Предусловия:**
  - Пользователь имеет действующий (valid) сертификат КЭП, выпущенный аккредитованным УЦ
  - Сертификат не числится в CRL (не отозван)
  - ИНН/ОГРН, привязанный к сертификату, присутствует в базе разрешенных пользователей ЛК
  - CRL-сервер УЦ доступен и отвечает в пределах 3000 мс
  - Текущее время строго меньше даты окончания сертификата
* **Шаги воспроизведения:**
  1. Отправить POST-запрос на эндпоинт `/api/v1/auth/kep` с корректным PKCS#7/CMS-сообщением, содержащим валидный сертификат КЭП и подпись
  2. Проверить HTTP-статус код ответа
  3. Проверить наличие поля `access_token` (JWT) в теле ответа
  4. Декодировать JWT-токен (base64url) и проверить содержимое поля `exp`
  5. Вычислить разницу между `exp` и `iat` (в минутах)
  6. Проверить, что поле `sub` или `inn` содержит ИНН, привязанный к сертификату
  7. Использовать полученный JWT-токен для запроса к защищенному ресурсу (например, `GET /api/v1/user/profile`)
* **Ожидаемый результат:**
  - HTTP-статус: **200 OK**
  - Тело ответа содержит `{"access_token": "<JWT>", "token_type": "Bearer", "expires_in": 900}` (expires_in = 15 минут × 60 секунд)
  - `exp` — `iat` = 900 секунд (15 минут)
  - Поле `inn` в JWT совпадает с ИНН сертификата
  - Запрос к защищенному ресурсу с JWT-токеном возвращает **200 OK** и данные профиля
* **Тестовые данные:**
  - PKCS#7 сообщение: валидный CMS с сертификатом серийный номер `A1B2C3D4E5F6000100020003`, ИНН `7701002001`, срок действия `valid_from=2026-01-01T00:00:00Z`, `valid_to=2027-01-01T00:00:00Z`
  - Подпись: корректная КЭП-подпись (PKCS#7 SignedData)

#### ТЕСТ-КЕЙС: TC-SCN-001-02 — Повторная авторизация с тем же сертификатом (новый JWT)
* **Тест-сьют:** 01 — Позитивные сценарии (Happy Path)
* **Тип проверки:** Позитивная
* **Приоритет:** Normal
* **Предусловия:** Предусловия TC-SCN-001-01 выполнены. Предыдущий JWT-токен ещё действителен.
* **Шаги воспроизведения:**
  1. Выполнить успешную авторизацию по TC-SCN-001-01, получить JWT-токен №1
  2. Немедленно отправить повторный POST-запрос на `/api/v1/auth/kep` с теми же данными сертификата
  3. Получить JWT-токен №2 из ответа
  4. Сравнить JWT-токен №1 и JWT-токен №2
  5. Проверить, что JWT-токен №1 продолжает работать для запросов к защищенным ресурсам
* **Ожидаемый результат:**
  - HTTP-статус: **200 OK** для обоих запросов
  - JWT-токен №1 и JWT-токен №2 — разные строки (разные `jti`, новый `iat`)
  - Оба токена валидны для доступа к API (не аннулируются при повторной авторизации)
* **Тестовые данные:** Те же, что в TC-SCN-001-01

#### ТЕСТ-КЕЙС: TC-SCN-001-03 — Неверный формат PKCS#7/CMS сообщения
* **Тест-сьют:** 02 — Негативные сценарии — Ошибки API
* **Тип проверки:** Негативная
* **Приоритет:** High
* **Предусловия:** Пользователь загружает файл в формате, отличном от PKCS#7/CMS (например, простой текст или JSON)
* **Шаги воспроизведения:**
  1. Отправить POST-запрос на `/api/v1/auth/kep` с телом, содержащим произвольную строку (не PKCS#7)
  2. Отправить POST-запрос на `/api/v1/auth/kep` с пустым телом
  3. Отправить POST-запрос на `/api/v1/auth/kep` с JSON-объектом вместо PKCS#7
* **Ожидаемый результат:**
  - Для всех трёх запросов: HTTP-статус **400 Bad Request**
  - Тело ответа: `{"error": "invalid_pkcs7_format", "message": "Неверный формат криптографического сообщения (PKCS#7 / CMS)", "code": "AUTH_040"}`
* **Тестовые данные:**
  - Запрос 1: `body = "this is not a PKCS7 message"`
  - Запрос 2: `body = ""`
  - Запрос 3: `body = "{\"key\": \"value\"}"`
