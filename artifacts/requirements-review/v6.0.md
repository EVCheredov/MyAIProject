# Requirements Review — EVC-001

**Фича:** EVC-001. Управление учётной записью и аутентификацией абонентов в личном кабинете «Super GSM»
**Источник:** Confluence (pageId=3407876), PII замаскирован инструментом Confluence
**Дата ревью:** 2026-11-15
**Процедура:** Parsing → Completeness Check → Consistency Check → Ambiguity Check → Boundary Analysis → Reporting

## Реестр замечаний

| REQ-01 | FR-01: «Ответ на неверный логин и на неверный пароль неразличим для клиента (защита от перебора логинов)» + FR-03: «возвращается HTTP 423 с телом {"errorCode": "ACCOUNT_BLOCKED", ...}» | Ответы различаются в зависимости от состояния учётной записи: HTTP 423 ACCOUNT_BLOCKED возвращается только для существующей (заблокированной) записи, тогда как для несуществующего логина — HTTP 401. Атакующий, отправив 3 неверных пароля на проверяемый MSISDN, получит 423 (учётная запись существует) либо 401 (не существует). Это ослабляет заявленную в FR-01 цель «защита от перебора логинов», но не является прямым противоречием (FR-01 говорит только о паре «неверный логин / неверный пароль»). | Medium | Задать единообразное поведение для несуществующего логина (например, «виртуальная блокировка»/обобщённый 423 без раскрытия существования) либо явно зафиксировать допустимость перечисления по статусу блокировки. |
| REQ-02 | FR-02: «Минимальная длина 8 символов, максимальная 64 символа… должен содержать не менее одной заглавной… строчной… и одной цифры» | Описаны правила политики пароля, но не описана бизнес-ветка отклонения: не определено поведение/ответ (HTTP-код, errorCode), когда вводимый пароль не соответствует политике (при установке, смене или восстановлении пароля). | Medium | Определить ответ при нарушении политики (HTTP-код + errorCode + текст), а также явно указать, к каким операциям применяется политика (смена, восстановление, первичная установка). |
| REQ-03 | FR-03: «После 3 последовательных неудачных попыток ввода пароля учётная запись блокируется» + FR-01: «При неверном пароле возвращается HTTP 401…» | Не определён порядок проверок для заблокированной учётной записи: (а) проверяется ли состояние «Заблокирована» раньше валидации учётных данных; (б) что возвращается при вводе неверного пароля на заблокированной записи — 423 или 401, и увеличивается ли счётчик; (в) продлевают ли попытки входа в период блокировки 30-минутное окно. Неоднозначность влияет на безопасность и на счётчик попыток. | Medium | Зафиксировать порядок проверок (blocked-check перед credential-check), поведение счётчика в период блокировки и ответ для заблокированной записи при любых входных данных. |
| REQ-04 | FR-04: «Время жизни сессии (TTL) — 30 минут с момента последней активности; каждая успешная операция продлевает TTL» | Двусмысленность «успешная операция»: не уточнено, какие именно запросы продлевают TTL (любой аутентифицированный запрос, только бизнес-операции, фоновые/служебные вызовы) и как учитываются параллельные запросы. | Low | Определить перечень операций, продлевающих TTL, и правило обновления «последней активности» при конкурентных запросах. |
| REQ-05 | FR-04: «При смене пароля все активные сессии абонента, включая текущую, инвалидируются» | Не определено, что происходит с текущей сессией сразу после успешной смены пароля: пользователь немедленно разлогинивается или получает новую сессию; также не описано поведение сессий при восстановлении пароля (FR-05). | Low | Уточнить пост-сменный сценарий (требуется повторный вход / выдаётся новая сессия) и поведение сессий после восстановления пароля. |
| REQ-06 | FR-05: «Код действителен 5 минут; допускается 3 попытки ввода кода, после чего код аннулируется» | Не определены ответы (HTTP-код/errorCode) для неверного SMS-кода и для истёкшего кода; не указано, что новый пароль после восстановления обязан соответствовать политике FR-02. | Low | Задать errorCode/HTTP для «неверный код» и «код истёк», а также явно указать применение политики пароля FR-02 к новому паролю. |

| REQ-08 | FR-01: «HTTP 401… AUTH_INVALID_CREDENTIALS» + FR-04: «HTTP 401, SESSION_EXPIRED» | Один и тот же HTTP 401 используется для разных условий с разными errorCode, но не определён приоритет при обращении к аутентифицированному эндпоинту с истёкшей сессией vs с неверными учётными данными. | Low | Уточнить приоритет проверки сессии и соответствующую пару HTTP/errorCode для смешанных случаев. |

## Проверенные измерения (для полноты картины)

- **Completeness Check:** Основные бизнес-ветки покрыты — успешный/неуспешный вход (FR-01), блокировка и авто/ручная разблокировка (FR-03), истечение сессии и смена пароля (FR-04), восстановление по SMS (FR-05), недоступность Auth Service и недоставка SMS (FR-06). Полностью отсутствующих критичных веток не выявлено; пробелы относятся к обработке ошибок валидации/кодов (REQ-02, REQ-06, REQ-07) — Medium/Low.
- **Consistency Check:** Явных взаимоисключающих правил нет. Требования FR-03/BR-01 (сброс счётчика после успешного входа и по истечении блокировки) согласованы. Требование FR-01 и ответы FR-03 создают риск перечисления (REQ-01) — Medium, не прямое противоречие.
- **Ambiguity Check:** «успешная операция» (REQ-04), пост-сменный сценарий сессии (REQ-05), «остаток» в retryAfterSeconds интерпретируется однозначно (секунды до конца блокировки).
- **Boundary Analysis:** FR-02 явно задаёт обе границы (8 и 64 включительно) — дефекта нет. FR-03 (3 попытки / 30 мин, обнуление счётчика) и FR-05 (5 мин / 3 попытки) — границы определены; незначительная неопределённость по поведению на границе отражена в REQ-07.
- **Телеком-логика:** Требование BR-02 явно фиксирует, что блокировка учётной записи не меняет статус SIM-карты в сети и не влияет на баланс — телеком-инвариант описан корректно. Тестовые данные соответствуют: пароль-пример `SuperGsm2024` (12 символов, содержит заглавные/строчные/цифры) удовлетворяет FR-02; MSISDN маскированы.
- **PII:** Текст получен из Confluence с выполненным маскированием; повторный `pii_scanner` не требуется.
