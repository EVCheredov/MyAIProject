## СКИЛЛ 2: Проектирование задач (Task Design)

### 1. Назначение (Purpose)
Трансформация декомпозированных требований, бизнес-логики и результатов анализа в атомарные, понятные и структурированные технические задачи (заявки/тикеты/задания) для исполнителей (разработчиков, тестировщиков, системных аналитиков).

### 2. Входные данные и Управление контекстом (Inputs & Context Management)
* **Согласованный текст требований:** Описание функционала или бизнес-процесса из текущего контекста диалога.
* **Критерии приемки (Acceptance Criteria):** Утвержденные условия, которым должен соответствовать готовый инкремент продукта.
* **Context Selection (Выборка):** Навык выбирает для работы только финальный перечень зафиксированных бизнес-требований и критериев приемки (AC). Промежуточные технические логи проверок системных требований опускаются.
* **Context Filtering (Фильтрация):** Скилл полностью очищает оперативную память от результатов выполнения Скилла 1 (таблиц рецензирования дефектов), чтобы избежать конфликта контекстов и исключить попадание забракованных требований в описание задач для Jira. Используются только актуальные сущности.
* **Sandbox Rule:** Агент использует только те сущности, параметры, роли и термины, которые явно упомянуты во входном контексте текущей сессии.

### 3. Процедура выполнения (Procedure)
1. **Декомпозиция фичи (Decomposition):** Разбиение крупного требования на логически изолированные, независимые и проверяемые задачи (например: создание API-метода, изменение схемы БД, разработка UI-компонента,包装 автотестов).
2. **Формирование заголовков (Title Engineering):** Создание кратких, емких названий для задач, отражающих суть изменений по принципу `[Действие]: [Объект/Компонент] — [Суть изменений]`.
3. **Формализация описания (Description Generation):** Написание технического контекста задачи: зачем она делается, какие системы затрагивает в рамках предоставленного контекста.
4. **Трансляция Acceptance Criteria:** Перевод бизнес-критериев приемки в четкий, проверяемый чек-лист технической готовности задачи (Definition of Done для конкретного тикета).
5. **Определение зависимостей (Dependency Mapping):** Указание логической последовательности выполнения задач (какой тикет блокирует другие, а какие могут выполняться параллельно).

### 4. Правила и ограничения (Rules)
* **Правило атомарности:** Одна задача должна решать строго одну изолированную техническую или бизнес-проблему. Если задачу нельзя проверить отдельно от остальных, она декомпозирована неверно.
* **Запрет на технический домысел:** Запрещено придумывать и указывать конкретные названия таблиц БД, классов, методов кода или эндпоинтов API, если они явно не описаны во входном контексте.
* **Формат вывода:** Каждая спроектированная задача должна выводиться как отдельный блок с четкой Markdown-разметкой:

```markdown
### ЗАДАЧА: [Название задачи]
* **Тип задачи:** [Разработка / Тестирование / Аналитика]
* **Описание:** [Что конкретно нужно сделать и какой технический контекст]
* **Предусловия / Зависимости:** [Что должно быть сделано до старта этой задачи]
* **Критерии приемки (Acceptance Criteria):**
  - [ ] Критерий 1 (Проверяемое утверждение)
  - [ ] Критерий 2 (Проверяемое утверждение)
```
