## СКИЛЛ 3: Проектирование тестов (Test Design)

### 1. Назначение (Purpose)
Преобразование технических и бизнес-требований в детальные, воспроизводимые и структурированные сценарии тестирования (тест-кейсы и чек-листы) для обеспечения максимального покрытия функционала и минимизации рисков пропуска дефектов.

### 2. Входные данные и Управление контекстом (Inputs & Context Management)
* **Текст требований и критерии приемки:** Описание логики работы системы из контекста диалога.
* **Технические параметры (опционально):** Спецификации API, структуры запросов/ответов, схемы данных из текущей сессии.
* **Context Selection (Выборка):** Из всего доступного объема сессии навык выбирает только функциональные параметры, технические ограничения, таблицы переходов состояний и схемы API/БД. Организационная и проектная информация (номера Jira-задач, спринты, дедлайны) полностью игнорируется.
* **Context Filtering (Фильтрация):** Скилл осуществляет дедупликацию сценариев. Если одно и то же поведение системы описано в требованиях разными словами, фильтр склеивает их в одну сущность, очищая оперативную память от дублирующих путей проверки перед непосредственным проектированием шагов (Step Generation).
* **Sandbox Rule:** Проектирование ведется исключительно для сущностей, интерфейсов и логических путей, присутствующих в текущем контексте.

### 3. Процедура выполнения (Procedure)
1. **Выделение сценариев (Scenario Identification):** Разделение логики на позитивные сценарии (Happy Path) и негативные сценарии (обработка ошибок, отказов, невалидных данных, ограничений).
2. **Применение техник тест-дизайна:** Применение методов эквивалентного разделения и анализа граничных значений для параметров, указанных в требованиях. Формирование матрицы переходов состояний, если поведение сущности зависит от ее статуса.
3. **Разработка структуры (Test Suite Structuring):** Группировка тест-кейсов в логические папки/сьюты по функциональным блокам.
4. **Пошаговое описание (Step Generation):** Создание однозначных, последовательных шагов для воспроизведения каждого сценария.
5. **Формулирование ожидаемых результатов (Expected Results):** Описание точного эталонного ответа или состояния системы для каждого тест-кейса на основе требований.

### 4. Правила и ограничения (Rules)
* **Правило воспроизводимости:** Каждый шаг тест-кейса должен быть написан в повелительном наклонении и быть атомарным. Формулировки должны исключать двусмысленность выполнения.
* **Запрет на абстрактные данные:** Вместо фраз *«Ввести валидное значение»* агент обязан генерировать конкретные репрезентативные примеры тестовых данных на основе ограничений из контекста.
* **Формат вывода:** Сгенерированные сценарии должны выводиться в виде структурированного Markdown-списка:

```markdown
#### ТЕСТ-КЕЙС: [Уникальный ID / Название тест-кейса]
* **Тест-сьют:** [Название группы тестов]
* **Тип проверки:** [Позитивная / Негативная / Граничные значения]
* **Предусловия:** [Исходное состояние системы перед тестом]
* **Шаги воспроизведения:**
  1. [Действие 1]
  2. [Действие 2]
* **Ожидаемый результат:** [Что должна вернуть или сделать система]
* **Тестовые данные:** [Конкретные параметры для ввода: параметры API, строки, числа]
```
